# Generic subscription proposals — 16 November 2026

## Implementation

Admin RunScript automations containing SubscriptionProposal settings select candidate target entities and configured recipient groups after a durable entity.lifecycle.transitioned event. Native host validates enabled workspace categories/groups/transition IDs, internal recipients, subscription.create and record read access. Read-only script output cannot widen configured candidate/group scope or apply mutations. Defaults: PO Open→Issued triggers on current direct PO-line children; Sales & CRM delivery-completed fact and Quality document.uploaded; In-app only,365 days,exclude own changes. Admin edits definitions through existing Automations/category/lifecycle/group configuration UI. Setup.SubscriptionProposals.v1 preserves installed definitions and personal preferences.

New int-key tbl_SubscriptionProposal records each recipient/rule/target/trigger event exactly once, retaining pending/accepted/declined/unavailable status. Personal answer key SubscriptionProposal.Answer.{AutomationID}.{TransitionID} is stored in tbl_WorkspaceUserSetting for the actual user/workspace, with RuleId,TransitionId,Answer and a rule configuration hash. No workspace fallback permits administrative pre-consent. Changed configuration invalidates remembered applicability; renamed state labels preserve transition identity. Pending preference application works without an online browser. Answer writes lock the proposal/subscription and atomically save remembered preference, subscription and response; replay is idempotent. Disabled/config-changed/expired/unreadable/non-member proposals cannot install a watch.

SB_AutomationFiltersJson is nullable metadata on existing subscriptions; no key/index/relationship changes. State-kind matcher enforces event/destination-state filters; manual version/revision watches remain eligible. Combined automatic watches OR their filters; each filter retains its accepted channels, expiry and own-change choice. Per-hit channel metadata controls delivery creation and message contents, preventing cross-channel disclosure. Existing broader manual state watches are preserved; direct manual editing restores normal manual settings. Personal preference changes affect future/pending proposals, not historical accepted watches. Existing subscriptions remain user-managed.

The receipt transaction now appends purchaseorder.line.delivery.completed only after the final outstanding quantity is received. It rolls back with stock writes; partial/failed/retried fully-completed receipts do not add false completion events. Existing subscription delivery consumes it as a state-kind change. Supplier-upload routing continues through the existing document/owner read checks.

Global recipient dialog polls every15 seconds while signed in. It offers Yes/No, Remember and a five-minute session-only Ask later. User Settings has a Subscription Proposals tab with Ask/Always accept/Always decline, scoped to relevant/previously saved rules. Rule settings/raw event names are kept out of the question body. No permissions are granted by either consent or group selection.

## Limits

Proposal generation is event-driven and does not retroactively subscribe old already-issued orders. Browser questions wait for outbox processing/online polling; notification delivery retains its existing bundling delay. One active subscription per person/record means cancellation and stop-after-first remain record-wide; event filters retain their own channels/expiry/own-change rules. Declining future proposals does not cancel an existing watch. The generic selection scope supports the changed record and current direct children, not an arbitrary graph traversal. Task/email channel delivery was not sent in the local consent tests. Skipped cases are not passing evidence.

Fresh feature setup also grants **subscription.create** to the two seeded recipient roles so their members can consent to their own watches. It grants no entity/file read or subscription-assignment rights. Administrators can change this under group grants, and the installed seed marker preserves later removals. Users still need normal record access.
